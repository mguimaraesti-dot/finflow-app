# 0003 — Isolamento por espaço com Row-Level Security

Data: 25/11/2026 · Status: aceita

## Decisão
- Três papéis no Postgres:
  - `finflow_owner`: dono do schema; roda migrations.
  - `finflow_app`: grupo sem `BYPASSRLS`, com as permissões de tabela.
  - `finflow_api`: login da API, membro de `finflow_app`.
- A API abre uma transação por operação e define `app.user_id` (`withUser`). As políticas usam
  `app.is_member(workspace_id)` e `app.can_write(workspace_id)` (funções `SECURITY DEFINER` para
  não cair em recursão na tabela `memberships`).
- Criar espaço e aceitar convite passam por funções (`app.create_workspace`, `app.accept_invite`)
  porque quem cria ainda não é membro quando a linha nasce.
- Tabelas de identidade (`users`, `sessions`, `password_resets`, `consents`, `idempotency_keys`)
  ficam fora do RLS: só a API as acessa e elas não pertencem a um espaço.
- `audit_logs`: o papel da aplicação só insere e lê; não altera nem apaga.

## Por quê
Um bug de filtro na API não pode expor dados de outra pessoa. O RLS é a segunda barreira, testada
direto no banco (`apps/api/test/isolation.test.ts`).

## Em produção (Supabase ou outro Postgres gerenciado)
1. Criar os papéis com o script `scripts/db-setup.sh` (adaptando senhas) ou pelo SQL equivalente.
2. Rodar migrations com `DATABASE_URL` do `finflow_owner`.
3. Configurar a API com `DATABASE_URL_APP` do `finflow_api`. Senhas só nas variáveis de ambiente.
